# RViz 起飞前 odom 接收超时

2026-10-16。场景为隔离 PX4 1.17 / Baylands 全图，事件执行器、位置 External Vision 与原有安全门槛。

## 用户运行证据

`outdoor_20261016_114621` 在选择两点并按开始后，以 `FAST-LIVO2 receipt age exceeds 250 ms` 结束。它不是飞行中绕障失败：只进入 `prestream`，没有发出解锁命令，没有执行爬升或航点；最后状态未解锁，原 PX4 参数与执行源码保持不变。

| 事件 | 仿真时间 | 监督器 odom 接收年龄 |
| --- | --- | --- |
| 按开始 | 263.960 s | 18.7 ms |
| 起飞前预发送开始 | 270.552 s | 128.3 ms |
| 保护中止 | 271.140 s | 252.5 ms |

中止墙钟 `574670279675454 ns`。独立监视节点在 `574670186664778 ns` 已收到测量时间 `271.128 s` 的 odom，距中止约 93 ms；监督器却仍使用 `271.000 s` 数据（测量年龄 140 ms，接收年龄 252.5 ms）。因此可确认监督器接收落后于独立监视节点，不能把消息接收超时直接解释成 FAST-LIVO2 算法耗时 250 ms。附近三次 LIO 更新耗时约 9.8、12.4、12.9 ms。

运行记录虽写 `execution_executor=events`，当时只在 `execute()` 内创建事件执行器。地面选点、预发送、起飞和恢复仍调用全局 `rclpy.spin_once()`，所以昨天已测的轨迹执行接收优化没有覆盖这次故障阶段。原运行没有起飞前执行器 trace，无法进一步量化该阶段的 DDS 排队、GC 和 CPU 调度各占多少。

## 修复

- 用单个 `MissionReceiver` 从地面准备持续到降落恢复，同线程执行回调，保留接收批次 4 ms / 最多 32 次追加调用。
- RViz 等待、起飞前健康等待、预发送、爬升、航向等待、保持、官方 RTL 和 Land 均通过同一接收入口；独立原生测试未配置任务接收器时保留原接收方式。
- 规划阶段仅加入 preview / bridge 节点，退出时移除它们，监督器继续接收。DDS 实体销毁与 trace 写盘延至恢复／降落后。
- 可选接收诊断从地面开始，覆盖原来没有记录的起飞前阶段。
- 保留 250 ms 消息年龄、20 ms 测量配对、0.20 m 高度差、20 Hz setpoint 及原有碰撞／轨迹约束。

## 交互界面阻塞补充

只统一接收器后的 `outdoor_receiver_ui_20261016_01` 地面等待 90 秒，再发送用户原第一个航点相同的偏移 `(6.568009,0.285020)` 并开始任务。它仍在 `prestream`、解锁前被 `ground-aligned height has no measurement pair within 20 ms` 拦下。中止时 odom 接收年龄只有 6.7 ms，但该监督器之前丢失了覆盖测量时间的 PX4 样本；独立监视节点中这些样本仍存在。原参数基线和执行源码保持。

新增 trace 记录故障附近二代 GC 墙钟约 79.3 ms、线程 CPU 34.9 ms；该区间存在回调空档。原 UI 定时器创建于诊断安装之后，尚未记录其完整回调耗时，因此不能把全部空档直接归因于 GC 或绘图。

检查发现 UI 每秒在控制线程重新构建并发送 543 个不变的区域标记。现在冻结区域标记缓存，航点／完成状态变化时才更新完整 MarkerArray；标记寿命不设限、话题 transient-local，晚加入的 RViz 仍可取得完整最新显示。离线无实际 DDS 发布的构建对比：旧版每次约 12.7～14.3 ms，新版无变化检查小于 0.005 ms；此数值不代表整条 DDS 或飞行延迟。首次构建仍在地面完成，真实的显示发布耗时由新 trace 检查。

计时器与新增订阅采用增量安装诊断，避免重复包裹，并补测原回调恢复。没有调整 GC 阈值或关闭回收，也没有扩大配对／年龄门槛。

## 验证

277 项回归通过，含事件与 ready-batch 两种接收器的起飞前／执行／恢复生命周期、原生接收回退、异常传播、回调边界、ROS 时钟和现有飞行门控。既有测试替身同步到统一接收入口，原判据不变。日志：本机 `astra/runtime/receiver_final_regression_20261016.log`。

`outdoor_receiver_ui_20261016_02` 使用缓存修复后的源码，但在运动程序启动前被地面 EV／全局原点初始化检查拒绝：命令 ACK 成功，本地位置变化超过原 0.03 m 上限。没有解锁命令，原参数与执行源码保持；不作为接收修复成功或失败的飞行证据。

`outdoor_receiver_ui_20261016_03` 完成 90 秒地面等待、预发送、起飞、航向等待、巡航高度调整，并实际交接 EGO。随后仍因测量年龄 268 ms 中止并安全降落上锁。该次证明前置阶段能够通过，不证明任务完成。新 trace 记录桥回调已在 `575664717480072 ns` 处理 `199.520 s` 的 odom，监督器在 `575664731174078 ns` 检查时仍使用 `199.420 s`，直到 `575664740342264 ns` 才处理同一新帧；独立监视节点更早收到它。UI 显示缓存没有消除所有节点间回调先后问题。

由此补充一次有界队列复查：仅监督器主循环遇到 odom 年龄或高度配对错误时，不发 setpoint，追加一次不等待新消息的接收批次，然后重新检查**全部**门控。追加批次仍检查原 4 ms 预算与最多 32 次追加调用；它不能抢占正在执行的 ROS 回调，不能当作硬实时 4 ms 保证。若仍超时／无配对，或出现 reset 等其他故障，立即失败。没有增加原 250 ms 年龄上限或 20 ms 配对容差，也不会无限等待；诊断保存复查与恢复次数。独立原生测试不启用该任务复查。

最终配置 `outdoor_receiver_ui_20261016_04` 完成 90 秒地面等待、用户原第一个航点偏移 `(6.568009,0.285020)`、EGO 绕过直线路径上的障碍、规划返航、降落上锁。`complete_route_verified=true`、`known_surface_blocked_path_avoidance_verified=true`。任务流程、全部曲线连续净空、动态约束和共享空域通过，EV XY/Z 实际融合；原 PX4 参数与执行源码保持不变，无 armed failsafe。

最终轮没有触发追加队列复查，所以不能用它声称已在飞行中实测到复查挽回；该分支由回归覆盖。显示计时器仍有单次约 83.9 ms 的墙钟耗时，不能声称所有暂停已消除；20 Hz 是目标频率，不是每个发送间隔恒为 50 ms。运动期间有起飞阶段允许的初始航向 reset，未把它写成“全程无 reset”。UI 仍有部分命令时间戳校验拒绝记录，心跳与开始任务最终被正常接收，本轮未因 UI 失联中止；其拒绝原因分布需要另行检查，不放宽命令新鲜度限制。
